\begin{topic}{2 \; Data understanding: sources, formats, SQL, nature of data}{cData}
\sub{Data warehouse (DW)}
\insight{Central physical repository for decision support: enterprise-wide, cleansed, standardised, mostly structured, analytics-ready. Often \emph{not} normalised. Fed by \term{ETL} (extract, transform, load) via staging area; data marts = subsets.}
\insight{DW properties: \term{subject-oriented} (by subject, decision-relevant, not by product/operation), \term{integrated} (many sources $\to$ consistent format), \term{time-variant} (time-stamped, time = key dimension), \term{nonvolatile} (not updated; obsolete data discarded).}
\insight{Operational OLTP DBs: designed independently for efficiency \& consistency $\Rightarrow$ integration needed for decision support.}
\sub{File formats}
\insight{\term{CSV}: tabular, plain text, lightweight; only for strictly tabular data with same attributes (no nesting / lists of lists).}
\insight{\term{XML}: markup, self-descriptive, user-defined tags; one root, every tag closed, case-sensitive, properly nested, attribute values quoted, entity refs (\texttt{\&lt; \&gt; \&amp;}); extensible; more overhead, larger \& slower than CSV.}
\insight{\term{JSON}: name/value pairs, \texttt{\{\}} objects, \texttt{[]} arrays; vs XML: no end tags, shorter, quicker, arrays. Both: human readable, hierarchical, widely parseable.}
\sub{Accessing remote data (APIs)}
\insight{\term{ODBC}: standard middleware API to databases, independent of DBMS \& OS; driver translates; SQL query passed to DBMS.}
\insight{\term{SOAP}: XML-based messaging \emph{protocol} (envelope, header, body, fault); transport-independent, standardised (WS*), built-in error handling, function-driven.}
\insight{\term{REST}: architectural \emph{style} over HTTP: GET read, POST add, PUT update, DELETE remove; mostly JSON; lightweight, fast, cacheable, data-driven.}
\sub{SQL}
\insight{Entity = one object (row/tuple); attribute = column; entity type $\approx$ table; \term{primary key} uniquely identifies an entity; \term{foreign key} refers to another table's key.}

SELECT s.skey, c.name FROM sale AS s INNER JOIN customer\\ \ AS c ON s.ckey=c.ckey ORDER BY s.ckey;\ \textrm{$\to$ (10,Anna),(11,Anna)}\\

\insight{customer JOIN sale: \term{INNER} matches only (2 rows); \term{LEFT} + Bram/NULL (3); \term{RIGHT} + sale 12/NULL (3); \term{FULL} all (4). Never ordered = LEFT + \texttt{skey IS NULL}; orphan sale = RIGHT + \texttt{name IS NULL}; all \texttt{ON sale.ckey=customer.ckey}.}
\sub{Nature of data}
\insight{Data = collection of facts (observations, experiments, transactions); lowest abstraction; \term{garbage in, garbage out} $\Rightarrow$ make data analytics-ready.}
\insight{\term{Structured} (processable as is: star ratings, word counts, category codes \emph{or} names, transaction value) vs \term{semi-structured} (XML) vs \term{unstructured} (review text, images): need text mining or conversion.}

\sub{Arrival of data \& drift}
\insight{Stream challenges: limited computation/storage (online processing), adaptation to change. Fixes: incremental computation (store partial sums; overflow risk), \term{forgetting} old instances, \term{windowing} (only most recent).}
\insight{Non-stationary $\Rightarrow$ ``the'' distribution varies over time; e.g.\ average monthly sales over 5 years mixes seasons/trends $\Rightarrow$ use recent window, compare with last month \& same month last year.}
\sub{Containers vs VMs \& orchestration (Docker)}
\insight{\term{Differ}: container has no own OS, \emph{shares} host resources; VM \emph{partitions} hardware (hypervisor + guest OS). \term{Same}: package app + dependencies (portable), isolate apps, add a layer to host OS (Docker Engine vs hypervisor), run apps in parallel (VM fewer; many containers at once on one Docker host).}
\insight{\term{Orchestration} = automated configuration, coordination, management, scaling \& maintenance of (many) containers, e.g.\ \term{Kubernetes}. Docker builds \& runs single containers (\texttt{docker run}); \texttt{docker compose} starts a small multi-container stack on one machine (app + database); an orchestrator does this across many machines: starting, restarting failed containers, scaling up/down.}
